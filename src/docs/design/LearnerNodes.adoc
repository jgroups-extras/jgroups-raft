= Learner Nodes
:author: José Bolina <jbolina@redhat.com>
:description: Documents the design of learner nodes in Raft.
:homepage: https://jgroups-extras.github.io/jgroups-raft

[abstract]
--
JGroups Raft defines the roles LEADER, FOLLOWER and LEARNER, without a distinct CANDIDATE role.
This document describes the LEARNER role, introduced in version 1.1.
It details the problems the role addresses, how it is implemented, and aspects that are out of scope.
--

== Introduction

Learner nodes are non-voting members within the cluster.
While learners receive replicated entries from the leader, they do not contribute to the quorum for replication or participate in leader elections.
In JGroups Raft, learner nodes bring some advantages:

Enhanced Read Scalability::
Learner nodes can serve read operations locally without impacting the quorum required for committing write operations.
They can also assist during maintenance or recovery scenarios.

Simplified Membership Changes::
The process of adding or removing nodes from the Raft cluster can be cumbersome and prone to errors.
Initializing new nodes as learners makes this process simpler and safer.

To understand the context, it is important to distinguish between two membership concepts in a JGroups Raft cluster: JGroups members and Raft members.
Before learners, JGroups Raft enforced a strict requirement for these two sets of members to be identical; a node would fail to start if it was a JGroups member but not a configured Raft member.
JGroups members comprise all nodes present in the current JGroups view.
Raft members are those nodes configured in the `RAFT.members` property, plus or minus the committed membership changes.
All changes to the Raft membership (e.g., adding a new node as a Raft member) are subject to the consensus protocol.

Learner nodes decouple JGroups membership from Raft membership.
Every Raft member is also a JGroups member, but the converse is not necessarily true.
In practice, this means the JGroups view (`JM`) could encompass a set of members `JM={A, B, ..., Z}`, while the Raft members (`RM`) consist of a subset, `RM={A, B, C}`.
Any nodes in the difference `JM - RM` (i.e., `{D, E, ..., Z}`) automatically function as learner nodes.

Learner nodes also come with certain considerations:

Increased Complexity::
A new role inherently adds complexity, particularly in handling edge cases to ensure safety properties are never violated.

Resource Consumption::
While learners can significantly aid in scaling the cluster, especially if dirty reads are permitted, they are not without cost and still consume computing resources.

== Implementation

`RAFT` identifies learner nodes by verifying whether its `raft_id` is one of the Raft members.
During startup, after the state machine and internal state have been initialized from the log, a node not listed as a Raft member transitions to the learner role instead of throwing an exception.
Consequently, an application instance can start and connect to the `JChannel` without modifications to the Raft member list, and begins operating as a learner.

The role is implemented by the `Learner` class, which extends `Follower`.
A learner operates like a follower, with specific restrictions.
It receives requests from the leader to replicate entries and applies them to its local log.
It also sends append result acknowledgments to the leader; this feedback is necessary for the leader to track the log offset for sending entries (to both followers and learners) and is particularly critical when a node starts with an empty log.
The key restrictions are:

Never Vote in Elections:: A learner node never becomes a leader or votes in an election.
+
`BaseElection` only considers current Raft members when counting the majority and the votes.
A learner receiving a `VoteRequest` does not reply.
A learner can still coordinate an election on behalf of the Raft members when it is the JGroups coordinator.

Never Count Towards Replication Quorum:: A learner's acknowledgment does not contribute to the commit quorum for an entry.
+
The learner replies to the leader with the append result, like a follower.
If the result was successful but originated from a learner, the leader disregards it for quorum purposes.
If the result was unsuccessful (e.g., a log mismatch), the leader processes it as it does for followers (e.g., for catching up).

Handle Operations:: A learner node still processes certain operations.
+
For read requests, learners can perform dirty reads from their local state machine, when the application allows them.
This capability significantly improves scalability for read operations.
Write requests arriving at a learner are redirected to the leader if the `<raft.REDIRECT />` protocol is present in the JGroups stack.

=== Membership changes

Promotion and demotion are regular Raft membership changes.
`addServer()` and `removeServer()` append an internal command to the log, which takes effect on every node when it is committed.
Only one membership change is in flight at a time (https://github.com/jgroups-extras/jgroups-raft/issues/175[#175]); further changes wait for the previous one to complete.

=== Promotion

A learner node is promoted to a follower (and subsequently may become a leader) through a membership change adding it to the Raft members.
After the change is committed, the node operates as a follower, participating in elections and replication quorums.

Initializing nodes as learners and promoting them later improves cluster scalability when adding new nodes.
An application utilizing JGroups Raft can launch a new instance.
Once this new instance's log is up-to-date with the leader (as a learner), an operator can initiate a membership change to promote it to a follower, if deemed necessary.

=== Demotion

A current Raft member is demoted to a learner node when a membership change removes it from the Raft member list while it remains a JGroups member.
This approach is useful during maintenance periods.
A node can be removed as a Raft member (becoming a learner), continue to serve reads (if configured) or redirect writes, and then be stopped without affecting the write quorum of the remaining Raft members.
When the node restarts, it resumes its learner role, synchronizing from its log state at the time of shutdown.

=== Usage

The primary goal of the learner role is to mitigate common operational errors and enhance operational ease-of-use.
The role simplifies cluster scaling (both up and down) and eases Raft membership management.
New nodes can join the JGroups cluster without immediately requiring a formal Raft membership change operation.
This approach addresses several challenges, including:

* The need for manual pre-configuration of a node before it starts to include it in the Raft membership.
* Difficulties in removing and restarting a voting node without impacting quorum.
* The availability gap <<raft>> experienced by new nodes when joining the Raft member list directly as voting members.

Applications can then start new nodes seamlessly.
These nodes join the JGroups cluster.
If they are not (yet) configured as Raft members, they automatically start as learner nodes and receive and replicate entries from the leader.
An operator can monitor the cluster (e.g., via JMX) to verify whether a learner has caught up with the leader's log and then, if desired, submit a membership change operation to promote the learner to a follower.

Leaving a node as a learner does not negatively impact the Raft members.
Replication continues to function correctly as long as a majority of Raft members are available.
Learners in the cluster continue to accept and handle operations as defined (e.g., serving dirty reads or redirecting writes).

== Non-goals

As described in the Raft dissertation <<raft>> and observed in other implementations <<etcd>>, the concept of learner nodes can encompass additional functionalities.
This section clarifies functionalities that are explicitly out of scope:

No Automatic Promotion:: A learner is never automatically promoted to a follower.
+
In the standard Raft protocol, reconfiguration (a membership change) is always needed to include a new member in the cluster, as this also serves as a discovery mechanism for the Raft algorithm itself.
Therefore, one must issue a membership operation for the leader to be aware of the new member.
An automatic promotion might make sense if the reconfiguration happens first and then, after the learner catches up, it promotes to a follower.
In the JGroups Raft context, this specific type of automatic promotion does not offer significant advantages.
JGroups inherently handles node discovery upon channel connection, so the leader is aware of new JGroups members (potential learners) without any Raft-level membership operations.
Thus, a Raft membership operation is only required when an explicit promotion of a learner to a follower is desired.

No Constraint on Learner Count::
There is no predefined constraint on the number of learners in the cluster.
A cluster could have multiple learners simultaneously, potentially exceeding the number of Raft (voting) members.

== Conclusion

Learner nodes enhance cluster scalability, improve operational scaling, and simplify management.
The design draws inspiration from the Raft dissertation <<raft>>, adapted to leverage the inherent strengths and functionalities of JGroups.

A JGroups member that is not part of the Raft membership operates as a learner node.
The learner replicates entries to its local log and handles operations (such as serving reads or redirecting writes), but it does not participate in the quorum for entry commitment or leader election.
