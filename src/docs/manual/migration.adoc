== Migration Guide

Guide to migrate your applications between different versions.
JGroups Raft follows semantic versioning for releases.
Patch releases work out-of-the-box without changes from the application's perspective.
Major and minor releases may require configuration updates, migration scripts, or adoption of updated APIs.

=== 2.0.0

For users migrating from 1.x to 2.0.x.

==== Minimum Java Requirement

JGroups Raft 2.0 requires **Java 17** or later (upgraded from Java 11 in 1.x).

==== Annotation-Based State Machine API (v2)

JGroups Raft 2.0 introduces an annotation-driven, strongly-typed state machine API centered around `JGroupsRaft<T>`.

In 1.x, state machines required manual byte serialization, manual operation IDs, and boilerplate dispatching:

[source,java]
----
// 1.x approach: manual byte dispatching
public class MyStateMachine implements StateMachine {
    public byte[] apply(byte[] data, int offset, int length) throws Exception {
        // manual deserialization and method routing based on byte codes
    }
}
----

In 2.0, you define your state machine interface using `@JGroupsRaftStateMachine`, `@StateMachineRead`, and `@StateMachineWrite`:

[source,java]
----
// 2.0 approach: declarative annotations
@JGroupsRaftStateMachine
public interface KeyValueStore {

    @StateMachineRead(id = 1)
    String get(String key);

    @StateMachineWrite(id = 2)
    void put(String key, String value);
}
----

Instances are created using the builder pattern via `JGroupsRaft.builder()`:

[source,java]
----
JChannel channel = new JChannel("raft.xml");
KeyValueStore stateMachine = new KeyValueStoreImpl();

JGroupsRaft<KeyValueStore> raft = JGroupsRaft.builder(channel, stateMachine)
    .raftId("A")
    .build();

raft.start();
----

==== Schema Validation & Evolution

With the annotation-driven API, JGroups Raft validates the state machine schema at startup against `schema.raft` stored in the log directory.
This prevents replay corruptions during node restarts and rolling upgrades.

* **Adding operations**: You can introduce new read or write methods with unique IDs.
* **Retiring operations**: If an operation is removed from the interface, declare it under `@JGroupsRaftStateMachine(retiredReads = {...}, retiredWrites = {...})` so that historic entries can still be validated during replay.

==== Stream-Based Snapshot API

`StateMachine` snapshot methods have transitioned from byte buffers to streaming I/O (`InputStream` and `OutputStream`) to efficiently handle large snapshots without excessive heap allocations.

==== LevelDBLog Removal

The deprecated `LevelDBLog` implementation has been completely removed.
Use `FileBasedLog` for persistent log storage. If you still have legacy LevelDB data directories from 1.0.x, use the `migrate_leveldb.java` migration tool described below before upgrading to 2.0.x.

=== 1.1.0

For users upgrading from 1.0.x to 1.1.x.

==== LevelDBLog is deprecated

To remove the use of abandonware, we marked `LevelDBLog` as deprecated and its implementation now delegates to `FileBasedLog`.
Since these logs utilize different formats, a migration procedure is needed to keep your data intact.
We have developed a script utilizing https://www.jbang.dev/[JBang] to migrate from `LevelDBLog` to `FileBasedLog`.
This procedure will migrate the existing files to the expected format and keep the original data.

The migration script is located under the `bin` folder in the project root with name `migrate_leveldb.java`.
These scripts are not shipped with the release.
Suppose you utilized JGroups Raft with LevelDB pointing to folder `/home/raft/data`.
You can utilize the migration script as:

[source,bash]
----
$ ./bin/migrate_leveldb.java /home/raft/data
----

This will read the data files at the given folder and transform to the expected format.
If the procedure fails during the migration, the new files will be cleaned up.
The new data will be placed in the same folder, so you can restart your application without changing properties.

If there is already data files with the format expected by the `FileBasedLog` the script will not run and exit.
To run the migration tool and ignore the existing files, use the `--force` flag when invoking the script.
This will copy the existing data to a `temp` folder (`/home/raft/data/temp`, using the previous example) and will proceed with the migration.
If there is a `temp` folder already, the script will not run.

NOTE: JBang allows running remote scripts. See https://www.jbang.dev/documentation/guide/latest/usage.html#urls-from-trusted-sources[JBang] for more information.
